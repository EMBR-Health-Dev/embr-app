# Evidence Model

Stage 4 of EMBR's clinical logic pipeline (see the `embr-clinical-logic` skill doctrine, and its `references/pipeline-architecture.md` and `references/taxonomy-building.md` for the full design this document and `apps/api/src/lib/clinical-interpretation.ts` implement).

```
SymptomLog / CycleEntry / Treatment
        ↓
Stage 3 — existing deterministic pattern detection
  (e.g. trends/co-occurrence.ts)
        ↓
Stage 4 — Evidence Based Interpretation  ← this document, this milestone
        ↓
Stage 5 — future AI explanation (not built yet)
```

## Why this layer exists

Before this milestone, EMBR had a real deterministic pattern engine (`co-occurrence.ts`, detecting when two symptom categories were logged together on enough days to be meaningful) and, separately, an AI narration layer (`brief.ai.ts`). But nothing sat between them. `brief.ai.ts` generates its narrative directly from symptom/cycle summaries — safely, because its prompt and deny-list are tightly constrained, but without any formal, sourced, reviewable statement of what the detected data actually means clinically.

The Evidence Model closes that gap. Its entire job is to answer one question, for a fixed, small set of patterns: **given that this pattern was detected, what does real evidence actually allow us to say about it — and how confident should that statement be?**

## Observation, pattern, interpretation, hypothesis — kept strictly separate

- **Observation**: what the logged data literally shows. "Night sweats occurred on 18 of the last 30 days." Produced by Stage 1/2 — raw, normalized data, no meaning attached.
- **Pattern**: what deterministic logic detected. "Night sweats and sleep disturbance were both logged on 6 of the same days." Produced by Stage 3 (`co-occurrence.ts`) — a named, testable, reproducible detection, still no clinical meaning attached.
- **Interpretation**: what evidence allows us to say about that pattern. "Night sweats have been associated with fragmented sleep in polysomnographic studies..." Produced by Stage 4 (this layer) — sourced, tiered, caveated, hand-curated.
- **Hypothesis**: something that may be worth exploring but isn't established. This layer deliberately does not produce hypotheses yet — every entry in the registry is a curated interpretation with real sources, not a generated guess. A future hypothesis-generation capability, if built, would need its own explicit, clearly-labeled category — never blurred into an interpretation's confident phrasing.

**Clinical conclusions are never generated by this layer, or any layer that exists in this codebase today.** That would require a validated clinical framework and formal review this system doesn't have.

## Evidence tiers

Three tiers, matching the doctrine exactly:

- **established** — a position statement/guideline from a major clinical body, or a well-replicated peer-reviewed finding (ideally with objective, not only self-reported, evidence). Framed to the user as confident/well-understood.
- **emerging** — directional peer-reviewed findings, not yet full consensus, or a less direct mechanistic relationship than an established one covering an adjacent pattern. Framed as "research suggests," never as settled fact.
- **thin** — plausible or clinically reported, but without strong peer-reviewed backing yet. No entry currently seeded at this tier — none of the three initial interpretations needed it, not because the tier is unused by design.

A tier is not a vibe. `HOT_FLASH:SLEEP_DISTURBANCE` and `NIGHT_SWEATS:SLEEP_DISTURBANCE` are deliberately tiered differently — established for the latter (night sweats directly interrupt sleep; backed by polysomnographic, not only self-reported, evidence) and emerging for the former (daytime hot flashes' relationship to sleep quality is real but one mechanistic step further removed) — even though both involve a hot-flash-family symptom and sleep. Getting this distinction right, rather than rounding both up to "established" because they're adjacent and both plausible, is the actual discipline this layer exists to enforce.

## Provenance

Every `ClinicalInterpretation` carries a `sources: EvidenceSource[]` array. Each source has:

- `title`, `organization`, `sourceType` (`position_statement` | `patient_education` | `peer_reviewed_study` | `validated_instrument`)
- `publishedOrUpdated` — free text, not a strict date, since a journal article's exact publication date and a patient-education page's "last reviewed" note are genuinely different kinds of provenance, and forcing both into one date semantic would itself be a small dishonesty about what's actually known
- `url` — real, checked, fetchable at the time it was added. Tested directly: no `example.com`, no placeholder text, must start with `https://`

The three sources currently seeded were found and verified with a live web search immediately before being written into the registry, specifically so they'd be current and real rather than reconstructed from training-data memory (which risks a subtly wrong title, date, or URL — itself a form of unintentional fabrication):

- The Menopause Society, "Hot Flashes" (patient education) — `menopause.org/patient-education/menopause-topics/hot-flashes`
- "Vasomotor symptoms in menopause: physiologic condition and central nervous system approaches to treatment," _American Journal of Obstetrics & Gynecology_, Feb 2007
- "Sleep Disturbances in Menopause: Neuroendocrine Mechanisms and Clinical Implications," MDPI peer-reviewed review, 2026

## How the lookup works

```ts
getClinicalInterpretation(patternId: string): ClinicalInterpretationResult
```

Synchronous, deterministic, in-process — no LLM call, no network request, no database read. `patternId` for the co-occurrence pattern family is built with `coOccurrencePatternId(categoryA, categoryB)`, which sorts its two arguments before constructing the ID, so the same pair of categories always produces the same ID regardless of argument order.

The result is a discriminated union with exactly two cases (a narrowed version of `pipeline-architecture.md`'s full three-case `Stage4Result` — "no pattern matched at all" is Stage 3's concern, handled by `detectSymptomCoOccurrence` returning `null` before this function is ever called):

```ts
| { kind: "interpreted"; interpretation: ClinicalInterpretation }
| { kind: "noInterpretationAvailable"; patternId: string }
```

## Why unknown patterns return no interpretation, never a guess

This is the single most important property of this layer. If `getClinicalInterpretation` is called with a pattern ID that isn't in the hand-curated registry — because the pattern is real but hasn't been reviewed and sourced yet, or because it's not a pattern ID this layer recognizes at all — it returns `{ kind: "noInterpretationAvailable" }`. It does not attempt to construct a plausible-sounding statement on the fly. A future Stage 5 consuming this result should say, plainly, that EMBR doesn't have a validated read on that combination yet — never fill the silence with a fluent guess. An honest gap is a better outcome than a confident wrong answer, in this domain specifically.

## Why interpretations are curated, not generated

Every entry in the registry was written by a human (in this milestone, by Claude acting under explicit instruction, with real sources checked before writing), reviewed like content, and is immutable at runtime. Two users with the same detected pattern get the identical interpretation, every time — not a fresh generation that could subtly differ, drift toward overconfidence, or occasionally hallucinate a source. Adding a new interpretation is a deliberate, reviewable code change (a new registry entry, with real sources found and verified first), not something any request-time process can produce.

## Current registry (this milestone)

Three interpretations, all for the one pattern family that currently exists in this codebase (`co-occurrence.ts`'s category-pair co-occurrence):

| Pattern                              | Tier        | Why                                                                              |
| ------------------------------------ | ----------- | -------------------------------------------------------------------------------- |
| `HOT_FLASH` + `NIGHT_SWEATS`         | established | Same underlying vasomotor phenomenon, per The Menopause Society's own definition |
| `NIGHT_SWEATS` + `SLEEP_DISTURBANCE` | established | Direct, polysomnographically-documented sleep interruption                       |
| `HOT_FLASH` + `SLEEP_DISTURBANCE`    | emerging    | Real association, less direct mechanism than the night-sweats pair               |

Deliberately small. Not every symptom pair a user could log has, or needs, a curated interpretation yet — see the doctrine's own guidance on handling coverage gaps honestly.

## What this milestone does not do

- **Not wired into `brief.ai.ts`.** This layer exists and is independently tested; connecting it to BRIEF's narrative generation is real, separate follow-up work with its own review surface.
- **No Stage 5.** No AI explanation consumes this layer yet.
- **No new pattern types.** Only the existing co-occurrence pattern has interpretations; no new Stage 3 detection logic was added.
- **No database table.** The registry is in-code, hand-curated data — matching the doctrine's own "not generated per-request... looked up at runtime" framing, and appropriate at the current scale (three entries, changed by code review, not runtime mutation).
